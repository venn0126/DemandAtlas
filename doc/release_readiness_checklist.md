## 2. 文档目标

本文档用于在上线前进行统一核查，确保：

1. V1 范围内的功能完整可用
2. 主链路稳定
3. 边界状态可处理
4. 数据质量和结果质量在可接受范围内
5. 系统具备最小可观测性、限流和回退能力

### 2.1 使用方式

建议采用：

- `未开始`
- `进行中`
- `已完成`
- `风险接受`
- `不适用`

五种状态标记每个检查项。

## 3. 发布门槛定义

本项目 V1 建议采用三层发布门槛：

## 3.1 必须满足（Must Have）

不满足则不能上线：

- QueryTask 主链路可用
- ResultSnapshot 可读
- 热门榜可用
- 详情页可用
- 错误与空状态可处理
- 基础监控可用

## 3.2 建议满足（Should Have）

不满足可在受控前提下灰度，但需明确风险：

- 高增长榜稳定
- 导出稳定
- partial_success 体验良好
- 热门榜结果质量通过抽检

## 3.3 可后补（Nice to Have）

不阻断上线：

- 机会榜质量进一步优化
- 更丰富模板
- 更精细的 evidence 展示

- [ ] 用户可设置时间范围

- [ ] 摘要与 evidence 基本一致

## 16. 风险接受清单

以下风险若决定在 V1 接受，应显式记录：

- [ ] 机会榜质量仍较粗糙
- [ ] 地域线索能力较弱
- [ ] 部分模板质量参差不齐
- [ ] 聚类偶发不稳定
- [ ] opposing evidence 仍不够丰富

### 要求

每个被接受的风险，必须写清：

1. 风险描述
2. 影响范围
3. 为什么当前接受
4. 后续修复计划

---

## 17. 最终发布判断

## 17.1 可上线

满足以下条件时可进入灰度：

- Must Have 全部通过
- Should Have 大部分通过
- 已知风险有记录
- 监控与回退可用

## 17.2 建议延期

以下任一情况建议延期：

- 热门榜不可用
- QueryTask 状态不稳定
- ResultSnapshot 读取不稳定
- 前端主要状态流不完整
- 缺少基础监控或回退手段

## 19. 一句话结论

上线准备的关键，不是“大家觉得差不多可以上了”，而是：

> **用统一清单确认主链路、边界状态、结果质量、监控与回退都处于可接受状态。**
