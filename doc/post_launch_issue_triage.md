## 2. 文档目标

本文档用于统一 **需见** 上线后的问题分级、响应、决策和修复流程。

重点回答：

1. 什么问题算严重
2. 谁来响应
3. 什么时候该止血，什么时候该修复
4. 什么情况下要暂停灰度 / 回滚 / 关功能

---

## 3. 适用范围

本手册适用于以下问题：

- 功能故障
- 接口故障
- QueryTask 异常
- 排序与结果质量异常
- 导出异常
- 权限与匿名访问异常
- 发布后体验级重大问题

不适用于：

- 长期路线调整
- 非紧急产品讨论

---

## 4. 问题处理原则

## 4.1 先止血，再定位，再优化

处理顺序必须是：

1. 控制影响范围
2. 恢复主链路
3. 定位根因
4. 修长期修复

## 4.2 主链路优先

优先保护：

- 查询创建
- QueryTask 状态流
- ResultSnapshot 读取
- 热门榜
- 详情页

## 4.3 功能可降级，不强求全开

必要时优先关闭：

- 高机会榜
- 导出
- 非核心模板

不要为了保留全部功能而拖垮主链路。

## 4.4 结果质量问题也算线上问题

对于 **需见**，以下不只是“体验问题”，而是核心线上问题：

- 热门榜明显失真
- 增长榜被小样本污染严重
- 摘要与 evidence 明显冲突

---

## 5. 问题分级标准

建议统一使用 P0 / P1 / P2 / P3 四级。

## 5.1 P0：阻断级 / 立即止损

定义：

- 主链路不可用
- 错误会直接误导用户
- 存在安全或权限风险

典型场景：

- 无法创建 QueryTask
- QueryTask 大面积卡死 / 无结果返回
- ResultSnapshot 无法读取
- 热门榜结果明显错误且大面积出现
- 匿名 token 可访问他人任务
- 导出泄露非本人数据

处理要求：

- 立即响应
- 立即评估暂停灰度 / 限流 / 回滚 / 关闭功能

## 5.2 P1：高优先级 / 不可放量

定义：

- 主链路部分可用，但已有明显质量或稳定性风险
- 不建议继续扩大使用范围

典型场景：

- partial_success 比例异常升高
- 增长榜持续被小样本污染
- 详情页 evidence 大面积不可访问
- 导出成功率明显偏低
- 某一模板结果持续失真

处理要求：

- 当日处理
- 未修复前不建议放量

## 5.3 P2：中优先级 / 可带病运行

定义：

- 不阻断主链路
- 影响体验或结果可信度，但短期可接受

典型场景：

- 低置信度提示不够清晰
- QueryTask 页文案理解成本高
- 某些标签偶发错误
- opposing evidence 偶发缺失

处理要求：

- 纳入近期迭代

## 5.4 P3：低优先级 / 优化项

定义：

- 不影响主链路
- 不明显影响决策

典型场景：

- UI 间距问题
- 某处 copy 不够顺
- 某些列表交互可优化

处理要求：

- 进入产品优化池

---

## 6. 响应时限建议

| 级别 | 首次响应时间 | 初步结论时间 | 修复 / 止血目标 |
|---|---|---|---|
| P0 | 15 分钟内 | 30 分钟内 | 2 小时内给出止血方案 |
| P1 | 1 小时内 | 当日内 | 1 个工作日内完成或降级 |
| P2 | 当日内 | 2 个工作日内 | 进入下一迭代 |
| P3 | 正常排期 | 正常排期 | 后续优化 |

## 7. 角色分工建议

## 7.1 Incident Owner

每个问题必须有一个明确 owner。

职责：

- 收集问题信息
- 拉起协同
- 记录决策
- 推动关闭

## 7.2 技术 Owner

负责：

- 技术定位
- 日志与监控排查
- 修复方案

## 7.3 产品 Owner

负责：

- 判断影响范围
- 决定是否降级 / 关功能 / 暂停灰度
- 决定对外口径

## 7.4 数据 / 算法 Owner

负责：

- 排序 / 聚类 / evidence 类问题定位
- 结果质量修复建议

## 8. 标准处理流程

## 8.1 Step 1：记录问题

至少记录：

- 时间
- 发现人
- 环境
- 影响范围
- 截图 / 请求 / task id / snapshot id

## 8.2 Step 2：问题定级

按 P0 / P1 / P2 / P3 评估。

优先参考：

- 是否影响主链路
- 是否误导用户
- 是否影响数据或权限安全

## 8.3 Step 3：决定止血动作

可能动作包括：

- 暂停灰度
- 限流
- 关闭某榜单
- 关闭导出
- 限制模板范围
- 回滚版本

## 8.4 Step 4：定位与修复

包括：

- 技术定位
- 数据定位
- 结果复查
- 修复上线

## 8.5 Step 5：验证关闭

修复后必须验证：

- 问题是否复现消失
- 是否引入新问题
- 是否恢复放量条件

---

## 9. 止血动作清单

## 9.1 可快速执行的止血动作

### A. 限制模板范围

适用：

- 某类模板结果质量严重失真

### B. 关闭高机会榜

适用：

- 机会分明显误导用户

### C. 关闭导出

适用：

- 导出异常
- 下载链路不稳定

### D. 提高 QueryTask 限流

适用：

- 查询量过大导致系统不稳定

### E. 暂停 directed 大范围查询

适用：

- 大范围查询频繁 timeout

## 9.2 回滚触发条件

建议以下场景直接评估回滚：

- P0 连续出现
- 主链路大面积不可用
- 新版本明显引入严重结果失真

---

## 10. 结果质量问题专项处理

由于 **需见** 是结果型产品，需单独定义结果质量异常处理。

## 10.1 可视为 P1 / P0 的结果问题

### 可视为 P1

- 热门榜前列反复出现明显噪声
- 增长榜经常被极小样本占据前列
- 摘要与 evidence 偶发严重冲突

### 可视为 P0

- 榜单大面积把明显无关内容推到前列
- 结果明显误导用户判断
- 多模板同时发生系统性排序失真

## 10.2 处理优先级

处理顺序建议：

1. 热门榜
2. 增长榜
3. 详情页摘要 / evidence 一致性
4. 机会榜

## 13. 灰度期与正式上线期的差异

## 13.1 灰度期

原则：

- 更激进地止血
- 更保守地放量
- 更频繁地人工 review

## 13.2 正式上线期

原则：

- 更强调稳定性
- 更强调监控与自动告警
- 更强调问题归因与长期修复

---

## 14. 复盘触发条件

以下情况建议必须复盘：

- 任意 P0
- 同类 P1 一周内重复出现 2 次以上
- 结果质量问题导致灰度暂停
- 导出或权限问题引发用户风险

## 14.1 复盘产出建议

- 发生时间线
- 根因
- 哪个检查环节漏掉了
- 如何防止再次发生

---

## 15. 关闭标准

一个问题只有在以下条件都满足时才可关闭：

1. 已确认根因
2. 已完成修复或完成明确止血
3. 已完成回归验证
4. 不再继续影响灰度 / 上线判断

## 17. 一句话结论

上线后问题治理的关键，不是“出了问题再想怎么办”，而是：

> **提前定义分级、止血、修复和回滚机制，让需见在问题出现时仍然可控。**
