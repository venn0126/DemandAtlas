## 2. 文档目标

本文档用于把当前已经完成的产品、技术、接口、设计定义，收束成一个可以执行的 MVP 交付计划。

本文档重点回答：

1. MVP 到底要交付什么
2. 按什么阶段推进最稳妥
3. 哪些能力有依赖顺序
4. 每个阶段的完成标准是什么
5. 哪些事情必须上线前完成，哪些可以后置

---

## 3. MVP 交付目标

## 3.1 产品目标

在 V1 阶段交付一个可真实使用的 **Demand Atlas｜需见**，满足以下最小闭环：

1. 用户可以发起一键发现或定向发现
2. 系统可以通过 QueryTask 异步执行分析任务
3. 系统可以生成可复现的 ResultSnapshot
4. 用户可以查看热门需求榜和高增长需求榜
5. 用户可以进入需求详情页查看证据与解释
6. 用户可以导出基础结果

## 3.2 MVP 不追求的目标

V1 不追求：

- Reddit 全站全量覆盖
- 多平台支持
- 完整团队协作
- 复杂订阅系统
- 高级 AI 自动决策

## 3.3 成功定义

MVP 成功不等于“功能尽可能多”，而是：

> 用户能完成一次从查询到结果消费的完整闭环，并且结果足够可信、可解释、可导出。

## 4. MVP 范围确认

## 4.1 V1 必须交付

### 查询能力

- 一键发现
- 定向发现
- 时间范围选择
- active / new 视角支持

### 执行能力

- QueryTask 创建
- 缓存命中
- 异步任务执行
- 状态轮询

### 数据与分析能力

- 候选社区池 + 查询补拉
- 标准化帖子与评论
- 基础需求聚类
- discussion / attention / growth / opportunity 评分

### 结果能力

- ResultSnapshot
- 热门需求榜
- 高增长需求榜
- 高机会需求榜（辅助）
- 需求详情页
- supporting / opposing evidence

### 输出能力

- Markdown 导出
- CSV 导出

## 4.2 V1 可交付但可降级能力

若时间压力较大，可考虑以下能力“弱化交付”：

- 机会分先做弱展示
- opposing evidence 首版先少量展示
- 地域线索先保留输入字段，弱化真实过滤能力

## 4.3 V1 明确不交付

- 团队共享视图
- 收藏与需求库完整闭环
- 订阅提醒正式上线
- 第三方导出（飞书 / Notion）
- 多平台接入

## 5. 交付原则

## 5.1 先闭环，再优化

优先交付：

- 可完整跑通的主链路

再优化：

- 结果质量
- UI 精细度
- 性能体验

## 5.2 先热门榜，再机会榜

排序体系中，热门榜和增长榜更基础、更稳定，机会榜更依赖主观判断。

因此推进顺序建议：

1. 热门榜
2. 增长榜
3. 机会榜

## 5.3 先异步任务正确，再追求快

QueryTask 和 ResultSnapshot 的正确性优先于极限速度优化。

## 5.4 先固定结果结构，再微调视觉

结果字段稳定后再做高保真视觉微调，避免 UI 返工。

---

## 6. 阶段划分总览

建议将 MVP 交付拆为 6 个阶段：

1. 项目准备阶段
2. 核心后端骨架阶段
3. 核心分析闭环阶段
4. 前端主链路阶段
5. 联调与质量提升阶段
6. 上线准备阶段

### 阶段关系

```text
P0 准备
  -> P1 核心后端骨架
  -> P2 核心分析闭环
  -> P3 前端主链路
  -> P4 联调与质量提升
  -> P5 上线准备
```

---

## 7. 阶段计划详解

## 7.1 P0：项目准备阶段

### 目标

冻结 MVP 范围，固定实现边界。

### 关键产出

- MVP 范围确认
- 技术路线确认
- 主题模板首批清单确认
- 候选 Subreddit 池首批清单确认
- 数据接入方式确认

### 关键任务

- 确认匿名查询是否首版上线
- 确认导出是否登录后可用
- 确认 V1 默认仅英文
- 确认 NSFW / 私有 / 封禁社区排除策略

### 完成标准

- 项目边界清晰
- 关键定义不再频繁变化

---

## 7.2 P1：核心后端骨架阶段

### 目标

先建立系统骨架与核心对象。

### 关键产出

- 基础数据库表
- QueryTask 主流程骨架
- ResultSnapshot 主流程骨架
- TopicTemplate 基础能力
- 核心 API 雏形

### 关键任务

- 建立 `query_tasks`
- 建立 `result_snapshots`
- 建立 `demand_clusters`
- 建立 `cluster_metric_snapshots`
- 建立 `result_snapshot_clusters`
- 建立 `export_jobs`

### API 范围

- `GET /topic-templates`
- `POST /query-tasks`
- `GET /query-tasks/{id}`
- `GET /result-snapshots/{id}`

### 完成标准

- 可以创建 QueryTask
- 可以轮询任务状态
- 可以生成空壳 ResultSnapshot

---

## 7.3 P2：核心分析闭环阶段

### 目标

让系统能够真正从 Reddit 数据跑出需求结果。

### 关键产出

- 数据抓取与标准化流程
- retrieve / cluster / score / snapshot 主 Pipeline
- 热门榜与增长榜可用
- 需求详情数据可用

### 关键任务

- Reddit 数据连接器
- SourcePost / SourceComment 标准化
- 需求聚类实现
- Evidence 抽取
- 评分引擎实现
- ResultSnapshot 排名写入

### 完成标准

- 至少一个主题模板可跑通完整结果
- 热门榜有稳定输出
- 详情页有 supporting evidence
- 导出所需结构齐备

---

## 7.4 P3：前端主链路阶段

### 目标

完成用户可见主流程。

### 关键产出

- 首页
- 一键发现页
- 定向发现页
- 查询任务页
- 结果页
- 详情页
- 基础导出流程

### 关键任务

- 表单页面实现
- QueryTask 轮询实现
- 结果页榜单展示
- 详情页展示
- 错误态 / 空态 / partial_success 展示

### 完成标准

- 用户可从首页走到详情页
- 异步任务状态可感知
- 结果页与详情页状态完整

---

## 7.5 P4：联调与质量提升阶段

### 目标

把“能跑”提升到“可用”。

### 关键产出

- 前后端联调稳定
- 排序结果基础校准
- 错误处理稳定
- 导出链路稳定

### 关键任务

- QueryTask 边界 case 联调
- 空结果 / partial_success 联调
- 榜单与详情字段校验
- OpenAPI examples 对齐
- 前端状态恢复验证

### 完成标准

- 主链路稳定
- 常见错误可处理
- 结果结构稳定

---

## 7.6 P5：上线准备阶段

### 目标

确保可以对外提供可控的 V1 服务。

### 关键产出

- 上线配置
- 监控与告警
- 运行手册
- 风险预案

### 关键任务

- 基础监控接入
- 日志与错误追踪确认
- 查询限流策略确认
- 数据源失败预案确认
- 导出文件过期策略确认

### 完成标准

- 可灰度上线
- 有基本可观测性
- 有回退与降级方案

## 9. 依赖关系

## 9.1 关键前置依赖

### 前端依赖后端

- QueryTask API
- ResultSnapshot API
- Cluster detail API
- Export API

### 分析依赖数据

- Reddit 数据连接器
- 候选社区池
- 主题模板版本

### 排序依赖聚类

- 聚类稳定前，榜单质量不可稳定

## 9.2 推荐并行方式

可并行推进：

### 并行 A

- 后端骨架
- 前端页面骨架

### 并行 B

- 数据连接器
- TopicTemplate 配置

### 并行 C

- UI 基础组件
- OpenAPI examples / mock 数据

## 9.3 不建议并行的部分

不建议过早并行：

- 高保真 UI 精修
- 高级机会分优化
- 团队协作能力

## 10. 验收标准

## 10.1 功能验收

V1 至少满足：

1. 可发起 one_click 查询
2. 可发起 directed 查询
3. 可查看 QueryTask 状态
4. 可读取 ResultSnapshot
5. 可查看热门榜
6. 可查看高增长榜
7. 可查看详情页
8. 可导出 Markdown / CSV

## 10.2 状态验收

必须覆盖：

- cache hit
- async running
- partial_success
- success
- failed
- no result
- weak signal
- low confidence

## 10.3 质量验收

至少应满足：

- 热门榜可读
- 详情页有可解释证据
- growth 榜不会被极小样本完全污染
- partial_success 能被清晰感知

## 10.4 性能验收

目标：

- 常见缓存查询：10 秒内可见结果
- 异步查询：3 分钟内有结果或明确失败

## 11. 风险与缓冲

## 11.1 最大风险

### 风险 A：数据源不稳定

影响：

- fetch 阶段失败
- partial_success 频率高

### 风险 B：聚类质量不稳

影响：

- 榜单解释差
- 详情页不可信

### 风险 C：增长榜被小样本污染

影响：

- 产品可信度下降

### 风险 D：前端异步状态体验差

影响：

- 用户觉得系统卡死

## 11.2 缓冲建议

### 对数据风险

- 允许 partial_success
- 先聚焦核心社区池

### 对聚类风险

- 先从少量高价值模板开始
- 人工校验热门榜

### 对排序风险

- 机会榜弱化
- 热门榜优先稳定

### 对体验风险

- QueryTask 页必须优先打磨

## 15. 一句话结论

MVP 交付推进的关键，不是把所有想法一次性做完，而是：

> **先把 QueryTask -> ResultSnapshot -> Board -> Cluster Detail 这条主链路稳定交付出来，再逐步增强结果质量与扩展能力。**
